# Flood Evacuation Routing — Architecture and Design Decisions

## Project Overview

This app computes pedestrian evacuation routes from flood-affected buildings to the nearest safe building in Brandenburg, Germany. It combines the Copernicus Emergency Management Service flood mask, the OpenStreetMap road network, and OSM building footprints into a single routable graph, then exposes that graph through a Flask API consumed by a Leaflet single-page frontend. The core premise is that a road segment crossing a flood polygon should be penalized to infinity in the routing cost, so A\* naturally finds paths that avoid flooded streets or, if unavoidable, minimize exposure to them.

## Data Sources

The Copernicus EMS product EMSN068 provides the authoritative flood extent for the Brandenburg 2024 event as a shapefile of 198,254 individual parcel-level polygons. This source was chosen because it represents the official emergency mapping output and covers the exact event area rather than a modelled approximation. The Geofabrik OSM buildings shapefile for Brandenburg provides 76,950 building footprints clipped to the flood bounding box, chosen because it is freely downloadable in bulk and carries the polygon geometry needed for real-footprint display. The OSM road network was downloaded from Geofabrik as a `.osm.pbf` file and extracted to the study-area bounding box with osmium-tool, or via the OSMnx Overpass API fallback when osmium is not available; OSMnx was chosen because it handles the full OSM-to-NetworkX conversion pipeline including geometry preservation.

## Graph Design

The routing graph is a single undirected `networkx.Graph` containing three node types: building nodes (prefixed `B_`), flood-polygon metadata nodes (prefixed `F_`), and road nodes (prefixed `R` for original OSM nodes, `CUT_` for nodes introduced at flood-boundary intersections). Three edge types exist: `road_segment` edges carrying the street geometry and length, `accesses` edges connecting each building to its nearest road node via a cKDTree lookup, and no edges at all on flood-polygon nodes (they are metadata-only). A single graph was chosen over parallel subgraphs because A\* can then operate on a uniform structure without graph-stitching logic, and the heterogeneous node types are distinguished cheaply by a `node_type` attribute rather than by graph membership.

## Surgical Flood Cut

The previous approach marked an entire street edge as flooded whenever it touched any flood polygon, making whole streets impassable even when only a short section crossed the water. The current implementation replaces each intersecting edge with subsegments split at the exact entry and exit points of the flood boundary, so the dry portions of the same street remain usable.

A Shapely STRtree spatial index is built once over all flood polygons before processing begins. An STRtree organises geometries into a hierarchical tree structure by their geographic position — instead of checking all 198,254 polygons for every street edge, the index returns only the 2–3 nearby candidates in roughly logarithmic time. For each flooded edge, those candidate polygons are processed individually: the edge geometry is intersected with each polygon's boundary separately to find the exact points where the water starts and ends on that street. This per-polygon approach was chosen over merging the candidates into a single geometry first, because two nearby polygons with a gap between them must remain separate — merging them would incorrectly block the dry street segment between them.

Once the cut points are collected, intermediate nodes (prefixed `CUT_`) are inserted at those positions and the original edge is replaced by subsegments. Each subsegment's flood status is determined by checking whether its midpoint lies inside any of the candidate polygons. Subsegments where the midpoint is outside all polygons receive `flooded=False` and remain fully usable for routing.

## Routing

A\* pathfinding runs on the single graph using `routing_cost` as the edge weight: flooded `road_segment` edges and any edge with an unknown length receive `routing_cost = INF`, while dry edges receive `routing_cost = length` in metres. The heuristic is the Euclidean distance between a node's `x`/`y` attributes in EPSG:25832; road nodes carry these coordinates, but building and flood-polygon nodes do not, so the heuristic returns zero for them (making A\* degrade gracefully to Dijkstra's for those node types). The routing goal is the nearest building whose `flood_status` attribute is `safe`, found by running A\* towards each safe building and keeping the minimum-cost result.

## Building Classification

Buildings are classified into four ordered categories based on their spatial relationship to the flood polygons. A building that directly intersects a flood polygon is labelled `drowned`; one within a 10-metre buffer (but not intersecting) is `close_to`; one within a 50-metre buffer is `at_risk`; all others are `safe`. The classification uses GeoPandas spatial joins against the flood GeoDataFrame and its two buffered versions, and the categories are mutually exclusive by construction — each building is assigned the most severe category that applies. The result is stored as a `flood_status` node attribute on each building node in the graph so routing can query it directly without a separate lookup.

## Pipeline and Caching Strategy

All heavy computation runs in `prepare_datasets.py` before the server starts, never during request handling. The pipeline output is serialized to three files per dataset: `G.pkl` for the NetworkX graph (pickle, preserves the full node/edge attribute structure), `buildings.geojson` and `flood.geojson` for the GeoDataFrames. On server startup, `cache.py` loads every serialized dataset into RAM and immediately pre-serializes the buildings and flood GeoDataFrames to JSON strings; API endpoints for those resources return the pre-built string through a Flask `Response` object with zero per-request Python work, which reduces server latency from hundreds of milliseconds (iterrows + shapely_mapping on 76k–198k rows) to near-zero. Adding a new dataset at runtime through `POST /api/add_dataset` runs the full pipeline synchronously in the request thread and then adds the result to the in-memory cache.

## Frontend Design Decisions

The basemap is CartoDB Positron rather than OpenStreetMap because OSM tiles carry their own dense color scheme that competes visually with the flood-status color coding; the light-grey Positron background makes the red-orange-yellow-green building palette and the blue flood layer immediately legible. Buildings are rendered as real polygon footprints using Leaflet's `L.geoJSON` layer with `renderer: L.canvas()`, rather than as circle markers centered on building centroids; polygon shape communicates spatial extent more accurately, and the canvas renderer handles 76,950 polygons without the per-element DOM overhead that SVG rendering would impose. The map view is constrained to the flood bounding box on load via `setMaxBounds` and `setMinZoom(9)` so the user cannot accidentally pan to a blank world view. Flood polygons are simplified to a 0.0001-degree tolerance (roughly 8 metres) at cache-load time before serialization, reducing the transfer size from 109 MB to 13 MB; `smoothFactor: 2` is applied client-side on the flood layer for additional rendering simplification. The evacuation route is drawn as one `L.polyline` per graph edge rather than as a single merged line, so each segment can independently carry its flood status as a color (red for flooded, green for dry).

## Known Limitations

The `POST /api/add_dataset` endpoint runs the full pipeline synchronously inside the Flask request handler, blocking the server for the duration — typically 15 or more minutes for a new region. This is intentional for simplicity during the prototype phase but would need a task queue (e.g. Celery) before any multi-user deployment. The boundary-intersection logic in `cut_flooded_edges` handles `Point` and `MultiPoint` results correctly but falls back to marking the entire edge as flooded when the intersection returns a `GeometryCollection` containing non-point parts; this is a rare edge case for streets that run exactly along a flood boundary, and its frequency in practice has not been systematically measured. No authentication, rate limiting, or input sanitization is applied to the API endpoints, so the server should only be exposed on a trusted local network.
